# Commit

현재 프로젝트에서 변경사항을 분석하고, 승인받은 범위와 메시지로 커밋한다.

## 1. 변경사항 분석

- 프로젝트의 적용 가능한 `AGENTS.md`와 커밋 규칙을 확인한다.
- `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경사항을 모두 확인한다. 추적되지 않은 파일은 내용을 별도로 읽는다.
- Git 저장소가 아니면 상황을 알리고 중단한다. 임의로 `git init`하지 않는다. 변경사항이 없으면 커밋하지 않고 알린다.

## 2. 논리적 단위 분류

- 파일 경계보다 변경 목적을 기준으로 묶는다. 서로 독립적인 기능, 버그 수정, 리팩터링, 유지보수는 별도 커밋으로 제안한다.
- 같은 파일에 다른 목적의 변경이 섞여 있으면 필요한 부분만 스테이징할 계획을 세운다. 기존 스테이징 상태와 사용자 변경사항을 임의로 되돌리지 않는다.
- 사용자가 지정한 범위를 따른다. 관련 없는 변경사항을 자동으로 포함하지 않는다.

## 3. 한국어 메시지 작성 및 승인

커밋 제목은 `feat/fix/refactor/chore: 한국어 요약` 중 해당하는 형식으로 작성한다.

| 유형 | 기준 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 잘못된 동작 수정 |
| `refactor` | 외부 동작을 유지하는 코드 구조 개선 |
| `chore` | 설정, 의존성, 문서 등 유지보수 |

예: `feat: 컴포넌트 미리보기 기능 추가`

각 커밋의 포함 파일 또는 변경 부분, 변경 요약, 정확한 커밋 메시지를 사용자에게 제시하고 승인을 요청한다. 최초의 '커밋해줘' 요청을 제안에 대한 승인으로 간주하지 않는다. 제안된 범위와 메시지에 대한 명시적 승인을 기다린다.

## 4. 승인 후 커밋

- 실행 직전에 변경사항을 다시 확인한다. 승인 이후 범위나 메시지가 달라져야 한다면 수정된 제안을 다시 승인받는다.
- 승인된 파일 또는 부분만 명시적으로 스테이징한다. 기존에 스테이징된 관련 없는 변경이 있다면 함께 커밋되지 않도록 처리하며, 사용자의 작업과 기존 스테이징 상태를 보존할 수 없으면 진행 전에 확인한다.
- `git diff --cached`로 실제 커밋 대상을 확인한 뒤 승인된 메시지로 `git commit`한다. 여러 커밋은 승인된 순서대로 실행한다.
- 훅이나 검사에 실패하면 원인을 알린다. 훅을 우회하거나 승인 범위 밖의 수정사항을 자동으로 커밋하지 않는다.
- 완료 후 커밋 해시, 메시지, 남은 변경사항을 알린다. 별도 요청 없이 push, amend, reset 또는 이력 재작성은 하지 않는다.
